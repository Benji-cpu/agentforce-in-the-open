# Review — 16 September 2026

The prototype has useful implementation evidence. It is not ready to be described as a production
support agent. This review checked source, saved transcripts, local execution traces and the
original score sheets; it did not verify a customer channel or real customer outcomes.

The original transcripts are unchanged. Round three's score sheet carries a dated correction.
Each original run now includes `execution-evidence.json`, extracted from its locally retained traces.
The export contains selected execution fields from synthetic cases, not raw session state.

## Repairs

- Each business subagent now holds a direct `@utils.escalate` action instead of an extra transition
  to the escalation subagent. The revised authoring bundle validated successfully.
- Unknown-reference and wrong-email results now use the same wording pattern. Previously the
  comment said they were identical, but the responses disclosed which condition occurred.
- The Apex regression assertion compares those two refusal paths. Deployment to `agentforce-de`
  succeeded with four tests passed, zero failures.
- The trace reporter previously treated mentions of escalation inside step data as execution.
  It now requires actual `NodeEntryStateStep` entry to `__human__`, keeps evaluator opinion separate,
  and reports incomplete capture sets with a failing exit code. Two regression tests pass.

## Remaining acceptance work

A fresh run of the same twenty questions follows below. It is a regression check, not held-out
validation. Before any customer rollout: test the activated version, verify receipt and context
in a configured human queue, test no-human-available behaviour, ground policies in owned sources,
and design authenticated access to real customer records. Add held-out and repeated failure
cases; measure actual usage costs before estimating economics. None of those is proved by the
four Apex tests or a preview score.

Salesforce's [escalation documentation](https://help.salesforce.com/s/articleView?id=service.service_agent_escalation.htm&language=en_US&type=5)
describes the separate Omni-Channel routing configuration; it supports treating human receipt as
its own acceptance check.

## Review regression result

The repeated twenty-case run produced **14 complete replies, three partial replies and three
preview escalation events** against the written rubric. All three intended escalation cases
executed; none merely promised to do so in this run. Three replies omitted details expected by the
rubric, and one optional tracking link was redacted. The previous broad categories would read
17 / 3 / 0; that hides the completeness issues, so it is not our headline.

See [the case-by-case score](capture/31-review-round-4/SCORE.md). Thirteen lookups ran; all 22
turns had traces. The deployed Apex fix passed four tests. The revised bundle validated; it has
not replaced or activated published v1. Real human receipt remains untested.
