The reason for the build
“I am checking the status of your order.”

The first test sounded reassuring. The lookup never ran.

The agent’s user was missing permission to run the order lookup. In that preview, the action disappeared from the tools available to the model. The conversation did not explain the permissions problem.

After I assigned the permission, the same question ran the lookup and returned the order details. That small failure shaped the rest of the build: check the operation behind the words.

The finished demonstration looks up synthetic orders, reads published Knowledge articles and saves unresolved requests as Cases in a support queue. It returns a case number only after the record exists.

What this demonstration proves—and what it leaves open

The order action compares a supplied email and reference; it does not authenticate a customer. Policy answers read specific published Salesforce Knowledge articles using an Apex action; this is exact retrieval, not a vector-search benchmark. A queued Case proves a request was saved with context. It does not prove a person read it, and it does not connect a live chat or send an email.

A customer rollout would need an identity and access design, staffed queue ownership, monitoring, channel testing and a broader test set. No revenue, support-volume reduction or cost saving is claimed here.

How the build fits together

Agent Script routes the conversation to order, delivery, returns, calibration or support-request handling. Apex actions read the order, retrieve a published policy or create a Case. Permission sets control action and record access. The test harness saves the messages and traces; the support records are checked separately.
